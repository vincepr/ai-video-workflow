# Product video contract v1

Phase 01 fixes the shared request and context boundary. The browser and agent both call `normalizeRequest(draft, catalog)` from `scripts/product-video/request.mjs`; `source` is not serialized. `resolveContext(root, request, catalog)` returns an ordered manifest. `freezeRequest(root, request, manifest)` snapshots the selected input bytes and writes `request.json` once under `projects/<project-id>/work/product-video/<request-id>/`. `readFrozenRequest(root, projectId, requestId)` resumes that exact record. A changed draft needs a new UUID. These functions have no provider side effects.

The catalog path is `.agents/skills/generate-product-video/references/configuration/catalog.json`. Its stable version 1 shape is `{version:1, files:{router,common,workflows,formats,hooks,settings,styles,destinations}, choices:{direct:{formats,hooks,settings},skit:{styles},drama:{styles},"reference-remake":{styles}}}`. `files` maps IDs to repository-relative instruction paths. `choices` lists valid IDs per family. Recipe bodies stay in separate files. `none` hook and `auto` setting are valid choice IDs with no body. Phase 02 supplies real catalog data and may add metadata fields without changing these keys. Recipe and project files are copied into `inputs/000`, `inputs/001`, etc. The manifest keeps original paths, SHA-256 hashes, ordered roles and snapshot paths.

Request fields: `schemaVersion:1`, UUID `id`, `projectId`, `action` (`plan` or `generate`), `workflow` (`direct`, `skit`, `drama`, `reference-remake`), `choices` (direct: format, hook, setting; other families: style), `language`, `destination`, ordered `references` (`role`, project media path), `brief` (`product`, facts, brand, cta), and `execution` (`provider`, stage model IDs, durationSec, aspectRatio, imageResolution, resolution, audio, USD max budget). `imageResolution` controls image preparation; `resolution` controls video generation. Older frozen records without `imageResolution` retain their shared resolution value on retry and refinement without changing the frozen bytes. The contract validates selections and path scope; the launcher validates live provider capabilities and stage cost before submission. Browser/agent language matching happens before normalization; both pass canonical IDs.

There is no phase 01 CLI. The later launcher should expose one command that reads a frozen request by project ID and request ID, uses only the snapshot paths, and reports an unsupported capability without changing workflow or provider.

## Runtime state for later phases

Keep mutable state beside `request.json`, never inside it. Use one record per stage with status `pending`, `prepared`, `submitted`, `accepted`, `downloaded`, `failed`, `unsupported` or `complete`. Persist provider job IDs and receipts at `accepted` before polling. Distinguish accepted task, raw artifact and edited export as separate records. Verification is a separate `{offline, live, creative}` verdict; an offline pass does not imply live provider support or creative approval.

Refinement dependencies: changing facts, references, format, hook, setting, style, language, model or motion invalidates creative planning and dependent image/video/finish artifacts. Changing only captions, trim, hold, brand overlay or local audio invalidates the finishing export. Changing destination invalidates release copy/eligibility review. A new frozen request represents changed generation inputs; existing raw media and numbered exports remain intact. These are dependency rules for phase 07, not phase 01 runtime behavior.
